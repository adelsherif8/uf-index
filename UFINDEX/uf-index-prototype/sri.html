GitHub · so we can work at the same time

Think of GitHub as a shared folder with a memory. You never edit the shared copy directly — you make your own copy of the work (a branch), change it, and then ask for it to be merged in (a pull request). Adel reviews it, and only then does it join the main code. That's how two people work simultaneously without breaking each other's work.

Your daily loop — five commands, always in this order:
git pull origin main # 1 · get the latest code first, every day git checkout -b sri/scoring # 2 · make your own branch (name it after the task) … work, test, repeat … git add -A && git commit -m "scoring engine passes 8/16 tests" # 3 · save a snapshot git push origin sri/scoring # 4 · upload your branch # 5 · on github.com → "Open pull request" → Adel reviews & merges

Commit small and often — a commit is a save point you can always go back to. If anything ever feels broken, stop and ask Adel before deleting anything.

The build order · one step at a time, in order

  1. 1
    Set up (one sitting)

    Install Node LTS and Git. Make a GitHub account and accept Adel's repo invite. Create a free project on supabase.com. Install Claude Code and sign in. Done for day one.

  2. 2
    Load the database

    Download uf_index_schema.sql below. In Supabase → SQL Editor, paste and run the Phase 1 tables (listed at the top of the file). Then look at each table in the Table Editor until you can say what each one stores — that's the app's whole memory.

  3. 3
    First endpoint, with Claude

    Open Claude Code in the project folder and paste the starter prompt below. Goal: POST /assessments — the app sends form answers, you store them. Read every line it writes before accepting. Ask it "why?" whenever something is unclear — that's the tutoring.

  4. 4
    The scoring engine — your exam

    The score must be a pure function tagged formula_version. Download the QA Excel below: you are done when all 16 expected results match. Not 15. This is the same check as the "Verify all" button on the main page.

  5. 5
    Login + consent

    Turn on Supabase email login. When someone signs up, write their consent rows (health-data processing + optional coach visibility). This is a legal requirement, not a nice-to-have.

  6. 6
    History

    GET /me/latest-score and GET /me/history — exactly what the dashboard score card and trend chart need.

  7. 7
    Plus questionnaires

    Endpoints to save WHO-5, PSS-10, and PSQI answers and compute their official scores (WHO-5 ×4 → /100 · PSS-10 with 4 reversed items → /40 · PSQI's 7 components → /21). The prototype's Plus screens show exactly which questions and scales.

  8. 8
    Notifications + subscriptions

    Store Expo push tokens in devices. One scheduled job sends the Sunday 6 pm reminder. Subscriptions: when a user starts Plus, insert a trial row — no payment code in Phase 1.

  9. 9
    Hand it over

    Supabase is already hosted — share the API URL and keys with Adel. He connects the app, and the prototype's two-phone demo becomes the real thing.

Starter prompt · paste into Claude Code at step 3

# Copy from here You're helping me build the UF Index backend. I am learning backend development — explain what you're doing as you go, in simple terms, and keep changes small. Stack: Supabase (PostgreSQL) + TypeScript Edge Functions. Schema: uf_index_schema.sql in this folder — Phase 1 tables only (listed at the top). Task 1: build POST /assessments. - Validate inputs against the ranges in UF_Index_Test_Cases.xlsx ("How to test" sheet) - Store raw inputs in `assessments`, metric units - Compute the score ("Formula" sheet), tag it formula_version "proto-1", store in `assessment_scores`, return score + band + the five pillars - Write tests asserting all 16 expected results from the Excel — done means 16/16 green.
Golden rules
  • Raw answers are never edited or deleted — history is sacred.
  • Every stored score carries formula_version — the formula will change, and old scores must be recomputable.
  • Claude is the tutor, the 16 tests are the judge — if tests pass, you're right, whoever wrote the code.
  • Small commits, small pull requests. Stuck for 30+ minutes → message Adel.

Your to-do list · beyond the code

Four things that are yours to own alongside the build. Each one says exactly what "done" looks like.

  1. A
    Plus pricing research

    The app shows ₹399/mo as a placeholder — nobody has decided the real price. Look up what 4–5 comparable India wellness apps charge (e.g. HealthifyMe, Cult.fit, Ultrahuman, Headspace India), and write one short page: their prices, your recommended Plus price, and how "free with UFAS coaching" should work. Done = that page sent to Adel. Until then, Phase 1 records every Plus user as a free-trial row — no payment code.

  2. B
    The formula watch

    The prototype scores with a placeholder formula (US Navy body-fat + weighted pillars — the Excel's "Formula" sheet). Build everything with formula_version "proto-1". The day UFAS signs off the official formula, you implement it as "uf-v1", Adel regenerates the 16 expected values, and your job is to make all tests green again. Done = 16/16 on the new formula. This is why formula_version exists — old scores stay recomputable.

  3. C
    Store accounts — know the process, chase the parts that aren't yours

    Apple (1–3 weeks, the critical path): ① UFAS management gets a free D-U-N-S number at dnb.com (legal name + address must match exactly; 1–5 days). ② The person with signing authority (owner/executive — not you) makes an Apple ID with two-factor auth. ③ They enroll as an Organization in the Apple Developer app (required in India) — legal name, D-U-N-S, ufaslive.com, $99/yr. ④ Apple verifies in 3 days–2 weeks, sometimes with a phone call. ⑤ Then you accept your Developer invite in App Store Connect (Adel gets App Manager). Google: Play Console account, $25 once, verified in a day or two. Your part = steps ⑤ and Google, plus politely chasing management weekly until ①–④ are done. Both stores also need a privacy policy URL on ufaslive.com before submission.
